## 1. Cursor 本地化加载链（源码级追踪）

Cursor 是 VS Code 分支，本地化沿用官方 NLS 体系。调用链如下：

```
Electron 主进程
  └─ 读取 out/nls.keys.json      (1,150 模块 / 13,530 键)   键表
  └─ 读取 out/nls.messages.json  (13,530 条)               英文原文（逐位对应）
  └─ 扫描已装扩展的 contributes.localizations
       └─ 找到 languageId = "zh-cn" 的语言包
       └─ 按 translations[].id 匹配 bundle：
            id="vscode"            → translations/main.i18n.json
            id="anysphere.cursor-*"→ translations/extensions/*.i18n.json
  └─ 把结果通过 window configuration 下发
       └─ workbench.js::setupNLS()
            globalThis._VSCODE_NLS_MESSAGES = configuration.nls.messages
            globalThis._VSCODE_NLS_LANGUAGE = configuration.nls.language
            document.documentElement.lang = (zh-cn → zh-Hans)
```

**关键证据**（`out/vs/code/electron-sandbox/workbench/workbench.js` 实读）：

```js
function setupNLS(e){
  globalThis._VSCODE_NLS_MESSAGES = e.nls.messages;
  globalThis._VSCODE_NLS_LANGUAGE = e.nls.language;
  let a = e.nls.language || "en";
  a === "zh-tw" ? a = "zh-Hant" : a === "zh-cn" && (a = "zh-Hans");
  window.document.documentElement.setAttribute("lang", a);
}
```

并在 `workbench.desktop.main.js`（39.8 MB）中命中：

| 符号 | 命中次数 |
| --- | ---: |
| `_VSCODE_NLS_MESSAGES` | 2 |
| `contributes.localizations` | 5 |
| `languagePack` | 10 |
| `resolvedLanguage` | 1 |
| `vscode-language-pack` | 1 |

→ **语言包在 Cursor 中是一等公民机制**，不是外挂。这是本方案选择"语言包为地基"的根本依据。

## 1.1 NLS 合并与缓存机制（源码级确证，**部署必须理解**）

`out/main.js` 中存在函数（记为 `U9e`，约 offset 2,748,489），负责生成运行时译文表。
反混淆后逻辑如下：

```js
async function U9e({ userLocale, osLocale, userDataPath, commit, nlsMetadataPath }) {
  if (VSCODE_DEV || userLocale === "pseudo" || userLocale.startsWith("en") || !commit || !userDataPath)
      return defaultConfig();                       // ① 英文 locale 直接跳过整个语言包链路

  const packs  = await scanInstalledLanguagePacks(userDataPath);
  const langId = resolveLanguage(packs, userLocale);          // "zh-cn"
  const pack   = packs[langId];
  const mainI18n = pack?.translations?.vscode;                // 官方包 main.i18n.json 路径
  if (!pack || typeof pack.hash !== "string" || !mainI18n || !await exists(mainI18n))
      return defaultConfig();

  const cacheRoot = join(userDataPath, "clp", `${pack.hash}.${langId}`);  // ② 缓存根
  const commitDir = join(cacheRoot, commit);                              // ③ 按 Cursor commit 分目录
  const finalFile = join(commitDir, "nls.messages.json");
  const corruptMarker = join(cacheRoot, "corrupted.info");

  if (await exists(corruptMarker)) await rm(cacheRoot, { recursive: true, force: true });  // ④ 损坏标记→整目录重建

  if (await exists(commitDir)) return configFor(finalFile);   // ⑤★ 缓存命中：直接返回，永不重算

  const [, keys, defaultMsgs, bundle] = await Promise.all([   // keys=nls.keys.json, defaultMsgs=nls.messages.json
      mkdir(commitDir), readJson(keysJson), readJson(messagesJson), readJson(mainI18n)
  ]);

  const out = []; let i = 0;
  for (const [moduleId, keyList] of keys) {
    const mod = bundle.contents[moduleId];                    // ⑥ 确认 bundle 外层是 { contents: {...} }
    for (const key of keyList) {
      out.push(mod?.[key] || defaultMsgs[i]);                 // ⑦★ 逐键合并：语言包优先，缺失回退默认表
      i++;
    }
  }
  await writeFile(finalFile, JSON.stringify(out));            // ⑧ 写入缓存
  await writeFile(join(cacheRoot, "tcf.json"), JSON.stringify(pack.translations));
  return configFor(finalFile);
}
```

### 由此确认的四条硬事实

**① 运行时真正的译文表是缓存文件，不是语言包**
```
%APPDATA%\Cursor\clp\<语言包hash>.zh-cn\<Cursor commit>\nls.messages.json
```
本机实测（13,530 条），与默认表逐位比对后精确拆解：

| 类别 | 条数 | 说明 |
| --- | ---: | --- |
| 译文与英文不同 | 11,454 | 其中 11,429 条含中日韩字符，25 条为纯 ASCII 译文 |
| └ 含中日韩字符 | 11,429 | 真正显示中文的部分 |
| └ 纯 ASCII 译文 | 25 | 译文本身就是 ASCII（产品专名等） |
| 与英文完全相同 | 2,076 | 见下方拆分 |
| └ 语言包无此键（**真缺口**） | 1,971 | 运行时回退显示英文 |
| └ 语言包有键但译文＝英文 | 105 | `Ctrl` / `Shift` / `Alt` / `Command` / `{0}: {1}` 等**本应保留英文** |
| **合计** | **13,530** | ✓ |

> **★ 交叉验证**：`11,429 + 25 + 105 = 11,559`，与 §3.1 用键表独立算出的
> "已本地化 11,559" **逐条吻合**；剩下的 1,971 也与缺口数吻合。
> 两条完全不同的路径（键表比对 vs 运行时缓存比对）得出同一组数字，
> 说明 §3.1 的覆盖率统计可信，且 **1,971 是"需真正翻译"的正确口径**——
> 那 105 条不是缺口，翻译反而会出错。

**② 缓存按 `(语言包hash, 语言, Cursor commit)` 三级键控**
本机现存两个 commit 目录：`be4c9e5350d77747b42cd467cbd3370a753d4640`（＝当前 `product.json.commit`）
与 `37b86594…`（升级前的旧版本残留）。**旧缓存不会被自动清理。**

**③ ★ 缓存命中即短路，这是"汉化没生效"的真实根因**
第 ⑤ 步只要 commit 目录存在就直接返回，**根本不会重读 `nls.keys.json` / `nls.messages.json`**。
所以：改动语言包或默认表后，若不失效缓存，重启多少次都不会生效。

**④ 有两个可用的缓存失效手段**

| 手段 | 做法 | 风险 |
| --- | --- | --- |
| 删除缓存目录 | 删 `clp\<hash>.zh-cn\<commit>\` | 低（Cursor 会自动重建） |
| **投放损坏标记** | 在 `clp\<hash>.zh-cn\` 放一个空文件 `corrupted.info` | **更低——这是 Cursor 自带的修复通路**，第 ④ 步会整目录重建 |

**⑤ 第 ⑦ 步是"默认表通道"成立的依据**
`mod?.[key] || defaultMsgs[i]` —— 语言包没有的键，直接回退到 `out/nls.messages.json`。
而 `out/nls.messages.json` **不在 `product.json.checksums` 覆盖范围内**（见 §4.2）。
→ **改写这一个 665 KB 的免校验文件，即可让全部缺口键显示中文，
无需生成语言包、无需触碰任何被校验文件、无需重算哈希。**
代价：必须同时失效 `clp` 缓存（手段见上表）。

> 这条通道把 M2 的最坏风险从"改 39.8 MB 主 bundle + 重算校验"降到
> "改一个免校验的 JSON + 清缓存"，是本工程优先级最高的低风险路径。

### 3.2 路径漂移救回（关键发现）

实测语言包中**不存在** `vs/workbench/electron-sandbox/desktop.contribution`，
但**存在** `vs/workbench/electron-browser/desktop.contribution`。

原因为上游 VS Code 的 layering 重构：目录 `electron-browser` 被重命名为 `electron-sandbox`，
而语言包的 bundle 仍按旧路径组织，导致同模块译文全部对不上号（整模块 0% 覆盖）。

| 阶段 | 命中 | 覆盖率 |
| --- | ---: | ---: |
| 严格按 moduleId 匹配 | 11,559 | 85.43% |
| + 路径归一化映射（**映射上限**） | 11,891 | **87.89%** |
| └ 实现时 4 条占位符不匹配被闸拒后的**净**值（2026-10-15 实测） | 11,887 | **87.86%** |
| 再 + 全局同名键兜底（语义待核） | 12,403 | 91.67% |
| 严格净缺口（须真正翻译） | 1,127 | 8.33% |

已知有效的映射（来自实测）：

| 上游旧路径 | Cursor 新路径 |
| --- | --- |
| `electron-browser` | `electron-sandbox` |
| `contrib/search/common` | `contrib/search/browser` |

## 4. 修改通道分析（决定方案安全边界）

### 4.1 被校验的文件（6 个）

`product.json.checksums` 仅覆盖：

```
vs/base/parts/sandbox/electron-sandbox/preload.js
vs/workbench/workbench.desktop.main.js          ← 39.8 MB 主界面
vs/workbench/workbench.desktop.main.css
vs/workbench/api/node/extensionHostProcess.js
vs/code/electron-sandbox/workbench/workbench.html  ← 注入点
vs/code/electron-sandbox/workbench/workbench.js
```

**校验算法（已逐项复现）**：

```js
base64( sha256( fileBytes ) ).replace(/=+$/, "")   // 去掉 Base64 的 = 填充
```

验证结果：6/6 全部 MATCH。→ 改写文件后重算该值即可通过校验。

### 4.2 免校验的文件（重要）

| 文件 | 大小 | 是否被校验 |
| --- | ---: | --- |
| `out/vs/workbench/workbench.glass.main.js` | 47.4 MB | ❌ **免校验** |
| `out/vs/workbench/workbench.anysphere-ui-automations.js` | 8.9 MB | ❌ **免校验** |
| `out/vs/workbench/workbench.xai-commerce-prepaid.js` | 1.1 MB | ❌ **免校验** |
| `out/vs/workbench/workbench.glass.main.css` | 1.28 MB | ❌ **免校验** |
| `out/nls.messages.json` | 665 KB | ❌ **免校验** |
| `out/nls.keys.json` | 416 KB | ❌ **免校验** |

**战略含义**：智能体窗口（glass）与主进程消息表属于**免校验区**，
可作为低风险改造通道；而主 workbench 必须走"改写 + 重算校验"。

> 注意：不触发 checksum 校验 ≠ 无任何保护。Cursor 仍在启动时校验那 6 个文件，
> 因此任何方案都必须先备份、后写入，并提供还原。

### 4.3 CSP 约束（针对注入）

`workbench.html` 的 CSP：

```
script-src 'self' 'unsafe-eval' blob:        ← 无 'unsafe-inline'
require-trusted-types-for 'script'
trusted-types amdLoader ... dompurify safeInnerHtml anysphereUiPolicy ...  （无通配符）
```

结论：

1. **禁止内联 `<script>`**，注入必须是同源外部文件或 `blob:` URL
2. **`trusted-types` 白名单不含通配符**，第三方脚本无法自建任意名称的 policy
3. 运行时文本替换只能用 `textContent` / 文本节点操作，**禁用 `innerHTML` / `outerHTML` / `insertAdjacentHTML`**

## 5. 升级失配风险

| 变化项 | 影响 | 应对 |
| --- | --- | --- |
| `nls.keys.json` 键表变化 | 语言包译文对不上 | 每次升级后重跑生成器 |
| 模块路径再次重命名 | 大批量假缺口 | 归一化映射表需持续维护 |
| CSP / Trusted Types 收紧 | 注入失效 | 注入层做成可关闭的独立模块 |
| `product.json` 校验值变化 | 旧补丁触发"安装已损坏" | 重算 + 事务写入 |
| 界面文案缓存（`state.vscdb`） | 汉化"看起来没生效" | 提供缓存清理步骤 |
